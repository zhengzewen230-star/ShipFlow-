## 2. 编号与存储边界

`id` 是 `shipflow_qa.api_test_case` 的数据库自增主键，只用于行存储和关联；不要求连续，也不能作为业务测试编号。业务测试用例以唯一的 `case_no` 为准，例如 `TENANT-001`、`STORE-008`、`USER-020`、`RBAC-014`。

`shipflow_qa` 仅保存测试用例定义、请求模板、断言契约和运行状态；它不是业务夹具库、业务断言库或清理通道。未来真实 HTTP 自动化只能连接专用隔离后端，其业务库固定为 `shipflow_http_test`，不得连接或操作 `shipflow`、`shipflow_test`。

## 3. 业务流程与关键规则

平台管理员负责租户创建、查询、更新与状态变更；租户管理员只管理所属租户的店铺、用户、角色及角色权限关系。每次受保护请求必须在隔离后端重新确认当前用户、tenant_id、角色、权限、作用域、状态和逻辑删除条件。

写接口需要事务和幂等保护：同一 `Idempotency-Key` 与相同规范化请求只能产生一次业务副作用；同一键配不同请求必须按冻结合同返回冲突；过期版本必须返回 `COMMON-1005`，成功更新应递增版本。跨租户、已删除或不存在的资源必须按合同不可见；认证失败、权限不足和状态禁用必须分别验证对应响应与未发生的业务副作用。

## 4. 最终用例设计

所有面向人的 title、precondition、data_dependency 已中文化；`case_no`、module、test_type、priority、HTTP 方法、接口路径、JSON 字段名、占位符、权限码和错误码保持机器可识别形式。高风险权限边界、跨租户和重复写入场景被标记为 `P0`；幂等、版本、停用和并发类场景使用 `STATE_FLOW`，跨租户场景使用 `SECURITY`。

每条用例至少验证响应状态、业务错误码（适用时）、响应封装和 `X-Trace-Id`。核心写入场景的未来真实执行还必须在 `shipflow_http_test` 进行受限只读断言：tenant_id/作用域、状态、version、关联关系、幂等单一副作用及失败后数据未变。

## 5. 动态前置条件与数据隔离

真实执行需要四类最小权限身份：平台管理员、租户 A 管理员、租户 B 管理员、租户 A 低权限身份。资源按“租户 → 店铺 → 用户 → 角色 → 权限关系”的顺序由 API 或经批准的隔离夹具创建。

每次运行生成唯一 RUN_ID，并将此前缀用于租户编码、店铺编码、用户名、角色名、请求标识和幂等键。跨租户用例固定由租户 A 身份访问租户 B 资源。凭据、Token、Cookie 和连接串只能在运行时注入，不能写入 SQL、文档、日志或报告。

## 6. 清理、恢复与风险

资源清理顺序为“角色权限关系 → 用户角色关系 → 角色 → 用户 → 店铺 → 租户”。测试框架只能调用已冻结且经过批准的 API 恢复动作；不得猜测删除接口、直接写 SQL、绕过权限或修改共享账号/角色。若资源无法安全清理，必须保留 RUN_ID 和资源图，由隔离环境的 reset 责任人完成恢复。

当前风险包括：隔离后端尚未启动；四身份的真实权限映射、CSRF 写合同、可恢复 reset、角色夹具和业务库只读断言账户尚未完成真实验收。因此没有第二模块真实 pytest、HTTP 自动化、数据库断言或 Allure 报告可声明。

## 7. BLOCKED 转 READY 准入条件

仅当以下条件全部满足后，才可用单独、精确的状态升级脚本将获批的 case_no 转为 `READY`：

1. `shipflow_http_test` 与隔离后端已部署并证明不连接其他业务库；
2. 四类身份、最小权限、认证/CSRF 合同已完成真实验证；
3. 每个占位符均有受控运行时来源，且 setup、extractor、teardown 可由框架解析；
4. 每个写场景都有 API 恢复路径或已演练的整体 reset；
5. 对应接口已完成真实 HTTP 断言和 `shipflow_http_test` 只读数据库断言；
6. 幂等、版本、跨租户、权限和并发场景的错误矩阵与副作用均已验收；
7. 失败诊断、清理和报告均不会输出密码、连接串、Token 或 Cookie。

在上述条件未满足前，66 条用例必须继续保持 `BLOCKED`。
