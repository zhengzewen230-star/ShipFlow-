# 第二模块租户与 RBAC 接口自动化中文最终设计

## 1. 范围与运行状态

本设计覆盖第二模块冻结的 20 个业务接口，共 66 条用例：租户 17 条、店铺 17 条、用户 18 条、RBAC 14 条。USER-018、USER-019 已确认永久排除，不属于正式自动化范围。66 条全部保持 `BLOCKED`；这表示测试设计已冻结，绝不表示接口已执行或已通过。

认证、登录、CSRF 与会话刷新属于受保护接口的前置能力，归第一模块，不计入上述 20 个业务接口。

| 业务域 | 场景数 | 主要场景 |
|---|---:|---|
| 租户 | 17 | 创建、查询、更新、状态、未认证、平台边界、参数/重复、幂等、版本、并发 |
| 店铺 | 17 | 租户内 CRUD/状态、无权限、跨租户、参数/重复、幂等、版本、并发 |
| 用户 | 18 | 租户内 CRUD/状态、角色分配、无权限、跨租户、参数/重复、幂等、版本、角色作用域与外键 |
| RBAC | 14 | 角色与权限查询、角色权限替换、无权限、跨租户、权限外键、版本和停用状态 |

## 2. 场景分类与接口覆盖

20 个方法加路径组合以导入记录的 HTTP 方法与 request_path 为唯一合同。每个业务接口至少有主流程或失败合同；写接口覆盖幂等、重复请求或版本冲突时，必须同时验证 HTTP 响应和业务测试库的受限只读断言。

分类规则为：正常流程使用 `NORMAL`；参数、重复键和不存在依赖使用 `EXCEPTION`；未认证、无权限、跨租户使用 `SECURITY`；幂等重放、并发、停用状态和版本冲突使用 `STATE_FLOW`。P0 为权限边界、跨租户访问、幂等重复写和并发单副作用；其余正式合同为 P1。

## 3. 动态前置条件与数据隔离

运行只能连接隔离的 HTTP 后端与业务测试库 `shipflow_http_test`；用例定义库始终为 `shipflow_qa`。不得连接 shipflow 或 shipflow_test。运行时需要平台管理员、租户 A 管理员、租户 B 管理员及租户 A 低权限身份四类上下文，均按最小权限配置。

资源按“租户 → 店铺 → 用户 → 角色 → 权限关系”顺序由 API 或受控夹具创建。每次运行生成唯一 RUN_ID，并将该前缀用于租户编码、店铺编码、用户名、角色名和幂等键；所有资源必须带对应 tenant_id。跨租户场景固定由租户 A 身份访问租户 B 资源。

## 4. 断言、清理与失败恢复

每条用例验证响应状态、业务错误码（适用时）、响应封装和 `X-Trace-Id`。创建/更新/状态场景在 `shipflow_http_test` 中只读核对资源归属 tenant_id、状态、version 与单次副作用；跨租户和权限失败核对目标租户资源、版本及关系未变；幂等/并发核对同一幂等键只有一个业务副作用。

清理逆序为“角色权限关系 → 用户角色关系 → 角色 → 用户 → 店铺 → 租户”。失败时夹具记录资源图并继续尝试逆序清理；无法安全清理时保留唯一 RUN_ID 作为隔离证据，由隔离环境维护者使用受控 reset 恢复。自动化不得以生产库 SQL 或删除历史用例数据作为清理手段。

## 5. BLOCKED 转 READY 的准入条件

只有同时满足下列条件，指定 case_no 才可由单独升级脚本转为 `READY`：

1. 四类运行时身份、权限码及认证/CSRF 合同已在隔离后端真实验证；
2. `shipflow_http_test` 已具备可恢复的隔离 reset，且只读数据库断言账号和范围已批准；
3. 66 条用例的实际请求模板、占位符、setup/extractor/teardown 均由框架解析并通过单元测试；
4. 对应 HTTP 接口已完成真实验收，包含租户隔离、权限、幂等及版本断言；
5. 失败诊断和清理不会输出密码、连接串、Token 或 Cookie；
6. 状态升级 SQL 仅更新经批准的 case_no、automation_status、tags 与更新时间，并在事务内完成前后核对。

当前未满足项是隔离后端启动、四身份的真实凭据与权限映射、CSRF 写入合同、可用的业务测试库 reset、66 条真实 HTTP/数据库验收。故本轮不得运行 pytest，且不得将任何用例标记 READY。
