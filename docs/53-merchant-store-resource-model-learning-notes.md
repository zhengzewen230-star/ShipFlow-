# 店铺资源模型与迁移前门禁学习笔记

日期：2026-08-18（Asia/Shanghai）

## 结论

- `merchant_store` 不承载店铺默认地址、默认渠道或国家/地区；`shipment_address` 是订单快照，不能反向作为店铺配置来源。
- 店铺配置应使用独立的地址表和店铺-公共渠道关联表，并继续通过 `tenant_id + user_id + role + active sys_user_store_scope` 做资源隔离。
- V020 结构迁移和 V021 数据回填必须解耦；没有正式回填来源时，已有店铺保持未配置，不伪造默认值。

## 门禁经验

- 业务唯一性、停用行为和角色边界必须先冻结，才能确定数据库唯一约束和 API 行为。
- 迁移版本不能仅按文件名假定，必须以目标环境 Flyway 历史和 DBA 批准为准。
- 回滚不得触碰订单、报价和 `shipment_address` 历史快照；已有配置数据存在时不能简单 DROP 新表。
- 设计阶段只保留文档和静态证据，不能把静态契约写成已完成的运行能力。

## 对账确认后的学习结论（2026-08-19）

1. 资源模型设计和数据回填必须分离：缺失的 `warehouse`、`region_carrier_relation` 不能由 V021 代替，必须各自进行独立结构评审和迁移。
2. 任何主数据回填都必须先确认租户、店铺、平台、渠道和仓库的权威来源；重复编码或跨租户对象不能自动合并或迁移。
3. `STORE_EU_001` 的现有租户归属必须保留，`STORE_JP_001` 的非唯一归属必须先获得业务确认；平台编码不能凭名称推断。
4. V021 的边界固定为店铺地址、店铺渠道和地区关系的纯数据回填，并且必须具备批准的来源、幂等策略、备份和回滚方案。
5. 设计阶段可记录计划，但不能把未执行的 DDL、DML、Flyway 或静态契约写成已完成的运行能力。

当前门禁：自动匹配 0、业务数据写入 0、最高 Flyway 版本 V020、V021 不存在；P4-05/P4-06 保持 `BLOCKED`。
## 最终差异处理学习笔记（2026-08-19）

- 相同`store_code`不等于同一资源；`tenant_id`是店铺唯一归属的必要边界，不能用跨租户 upsert 覆盖。
- 重复店铺必须先由业务决定删除、停用或保留，技术侧只能按批准的完整主键范围执行。
- 店铺平台编码和物流渠道编码/承运商主键是两个独立域，不能通过名称或业务期望反推映射。
- 缺失主数据表必须独立进行 Schema 评审；V021 只承载纯数据回填，不能隐含 DDL。
- 回滚应绑定变更批次、主键范围、审计和备份点，禁止无条件 DELETE；订单、报价、轨迹、账单和历史快照永不纳入资源回填回滚。

当前结论：自动匹配 0、V021 未创建/未执行、数据库业务数据写入 0，P4-05/P4-06 继续 BLOCKED。
## P4-06 现有契约收口笔记（2026-08-19）

在资源表未回填时，正确行为是继续展示后端真实空值和中文不可用提示，而不是从订单地址快照、公共渠道或静态数量推断店铺配置。工作台和列表跳转也必须保留真实 query；当后端没有等价筛选时，应保留入口条件并提示契约缺失，不能前端过滤。
