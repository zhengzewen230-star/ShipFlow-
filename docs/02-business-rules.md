# ShipFlow 第一版业务规则

本文档将第一版已确认的业务决策编号化。所有规则均适用于对应租户范围，并应通过接口结果、持久化数据和审计记录进行验证。

## 一、租户与用户规则

### TENANT-001 租户代表签约商家主体

- 规则：一个租户只能代表一个签约商家主体；同一主体的店铺、品牌和平台账号归属于该租户。
- 正常场景：为一家中国跨境商家创建一个租户，并在租户下维护多个店铺。
- 边界场景：同一租户新增多个品牌或平台账号，不创建新的租户。
- 异常场景：试图让一个店铺同时归属于两个租户，系统拒绝并记录审计/安全日志。

### TENANT-002 租户下可管理多个业务账号

- 规则：一个租户可以管理多个店铺、品牌或平台账号，这些账号共享租户隔离边界。
- 正常场景：商家管理员为租户新增日本站店铺和美国站店铺。
- 边界场景：同一租户新增名称相同但平台账号标识不同的账号，按唯一平台标识区分。
- 异常场景：新增账号时绑定到不存在或其他租户，系统拒绝。

### TENANT-003 平台管理员创建租户和初始管理员

- 规则：只有平台管理员可以创建租户并指定初始商家管理员。
- 正常场景：平台管理员创建签约商家租户，并生成初始商家管理员。
- 边界场景：租户创建成功但初始管理员邀请尚未激活，租户保持待启用状态。
- 异常场景：商家管理员或操作员尝试创建租户，系统拒绝并记录安全日志。

### TENANT-004 商家管理员管理本租户用户和角色

- 规则：商家管理员只能管理本租户用户和角色，不能越权操作平台级角色或其他租户用户。
- 正常场景：商家管理员新增商家操作员并分配仓库或财务相关权限。
- 边界场景：商家管理员修改自己的非关键资料，但不能移除自己最后一个商家管理员权限。
- 异常场景：商家管理员为其他租户用户改角色，系统拒绝并记录安全日志。

### TENANT-005 禁止跨租户访问

- 规则：所有跨租户读取、修改、删除和关联操作必须被禁止，并记录安全日志。
- 正常场景：用户查询本租户订单，只返回本租户数据。
- 边界场景：请求中的资源 ID 存在但属于其他租户，系统按无权访问处理，不泄露资源存在性。
- 异常场景：篡改 `tenant_id` 或使用其他租户 Token 访问资源，系统拒绝并记录安全日志。

## 二、报价与订单规则

### QUOTE-001 同时计算商家申报重量和体积重量

- 规则：报价阶段必须支持商家申报重量和体积重量；体积重量依据渠道配置的体积系数计算。
- 正常场景：商家提交申报重量和长宽高，系统计算商家申报重量、体积重量并保留计算依据。
- 边界场景：商家申报重量等于体积重量时，计费重量取该相同值。
- 异常场景：申报尺寸、申报重量或体积系数缺失、为负数或单位非法，报价失败并返回明确错误。

### QUOTE-002 计费重量取最大值

- 规则：报价阶段计费重量取商家申报重量与体积重量的最大值。
- 正常场景：商家申报重量 2kg、体积重量 3kg，计费重量为 3kg。
- 边界场景：某一重量为零但另一重量有效，取有效重量；两者都为零时按渠道规则拒绝报价。
- 异常场景：计费重量使用仓库实际重量、平均值或较小值，属于报价阶段的业务错误，系统应拒绝或通过测试识别。

### QUOTE-003 渠道决定体积系数和进位规则

- 规则：体积系数和重量进位规则由物流渠道配置，不得由调用方随意覆盖。
- 正常场景：渠道配置体积系数和按 0.5kg 进位，系统按该版本计算。
- 边界场景：渠道规则版本切换后，新报价使用新规则，旧报价保留旧版本。
- 异常场景：渠道缺少有效规则或规则配置非法，系统不能生成可下单报价。

### QUOTE-004 报价必须有有效期和价格规则版本

- 规则：每个报价必须保存有效期、渠道规则版本和报价价格规则版本。
- 正常场景：在报价有效期内使用对应版本创建订单。
- 边界场景：在有效期截止时刻请求下单，按统一时区和边界约定判定是否有效。
- 异常场景：报价过期、版本缺失或报价被撤销，订单创建必须失败。

### ORDER-001 创建订单必须引用有效 quote_id

- 规则：创建物流订单时必须传入有效且属于当前租户的 `quote_id`。
- 正常场景：商家操作员使用未过期报价创建订单。
- 边界场景：报价属于当前租户但即将过期，系统以请求处理时刻校验有效性。
- 异常场景：缺少 `quote_id`、引用其他租户报价或引用过期报价，系统拒绝创建。

### ORDER-002 订单保存不可变报价快照

- 规则：订单创建时必须保存报价金额、计费重量、计费依据、渠道规则版本和有效期等不可变快照。
- 正常场景：订单详情可还原创建订单时的完整报价依据。
- 边界场景：报价后来失效或渠道配置更新，历史订单快照仍保持不变。
- 异常场景：订单读取时动态引用当前渠道价格导致历史金额变化，属于数据一致性错误。

### ORDER-003 渠道价格修改不影响历史订单

- 规则：渠道价格修改只影响后续报价，不得修改已创建订单的报价快照或已确认费用。
- 正常场景：调整渠道价格后，新报价使用新价格，旧订单仍使用原快照。
- 边界场景：订单复称触发重新计费时，只能依据订单允许的规则和确认流程更新费用。
- 异常场景：后台修改渠道价格后批量覆盖历史订单金额，系统必须阻止并记录审计。

## 三、仓库复称与价格确认规则

### ORDER-004 入库后保存仓库实际重量和尺寸

- 规则：包裹入库后由仓库人员测量并保存仓库实际重量和尺寸，并记录测量时间、时区和操作人；报价阶段的商家申报重量不被覆盖。
- 正常场景：仓库人员完成入库和复称，订单保存仓库实际重量、尺寸和复称记录。
- 边界场景：重复复称时保留历史测量记录，并明确当前生效记录。
- 异常场景：未入库就提交复称，或重量/尺寸为非法值，系统拒绝。

### ORDER-005 复称后按仓库实际数据重新计算计费重量和费用

- 规则：保存复称结果后，系统按渠道规则计算仓库实际体积重量，并取仓库实际重量与仓库实际体积重量的最大值作为复称后的计费重量，再重新计算费用。
- 正常场景：复称后根据仓库实际重量和尺寸计算出新计费重量并生成费用调整记录。
- 边界场景：复称后的计费重量和费用与原报价一致，费用不变并自动继续履约。
- 异常场景：规则版本缺失、计算失败或金额精度异常，订单不得静默出库，必须进入可处理异常。

### ORDER-006 费用降低时自动更新并记录调整

- 规则：复称后费用降低，系统自动更新订单当前费用，并记录调整前后金额和原因。
- 正常场景：复称结果使费用从 100 降为 90，系统自动更新为 90。
- 边界场景：费用仅因精度计算产生最小单位变化，按统一金额精度判断是否降低。
- 异常场景：费用降低但未记录调整审计，属于不可接受的数据追溯缺失。

### ORDER-007 费用增加必须人工确认

- 规则：复称后费用增加时，订单进入 `PENDING_PRICE_CONFIRMATION`，商家确认新价格后才允许出库。
- 正常场景：商家确认增加后的价格，订单转为 `READY_FOR_OUTBOUND`。
- 边界场景：重复确认相同价格应幂等，不重复产生调整记录。
- 异常场景：未确认新价格直接出库，系统拒绝并记录非法操作。

## 四、订单状态规则

### ORDER-008 订单必须遵循状态机

- 规则：订单只能沿 `DRAFT`、`PENDING_INBOUND`、`INBOUND`、`READY_FOR_OUTBOUND`、`OUTBOUND`、`IN_TRANSIT`、`DELIVERED` 的合法路径推进；费用增加时允许进入 `PENDING_PRICE_CONFIRMATION` 分支。
- 正常场景：订单按仓库入库、出库、运输和签收顺序推进。
- 边界场景：订单进入 `PENDING_PRICE_CONFIRMATION` 后确认价格，再回到可出库路径。
- 异常场景：从 `DRAFT` 直接跳到 `IN_TRANSIT`，系统拒绝并记录异常。

### ORDER-009 终止和特殊状态独立处理

- 规则：`CANCELLED`、`RETURNED`、`LOST` 为终止或特殊状态；地址异常、清关异常、运输异常使用独立异常单，不伪造为普通订单状态。
- 正常场景：运输丢失创建异常单并将订单置为 `LOST`。
- 边界场景：已 `DELIVERED` 订单后续发现索赔事项，保留交付状态并通过异常单处理。
- 异常场景：通过修改普通轨迹状态直接把订单从 `DELIVERED` 回退为 `IN_TRANSIT`，系统拒绝。

### ORDER-010 创建物流订单必须支持幂等

- 规则：
  1. 创建订单必须传入 `idempotency_key`。
  2. 同一租户相同 `idempotency_key` 只能创建一个订单。
  3. 相同幂等键和相同请求参数重复提交时，返回原订单结果。
  4. 相同幂等键但请求参数不同，返回幂等冲突错误。
  5. 不同租户允许使用相同 `idempotency_key`。
  6. 并发请求不得产生重复订单。
  7. 数据库使用 `UNIQUE(tenant_id, idempotency_key)` 保证最终一致性。
- 正常场景：同一租户以相同幂等键和完全相同请求重试，系统返回首次创建的订单结果，不新增订单。
- 边界场景：两个不同租户使用相同幂等键，可以分别创建各自租户的订单；同一租户的重复请求仅字段顺序不同但业务参数等价，仍返回原订单结果。
- 异常场景：同一租户相同幂等键提交不同 `quote_id`、地址、包裹或商品参数，返回幂等冲突错误；并发创建时数据库唯一约束只允许一个请求成功，其余请求读取原订单结果或返回冲突。
- 并发测试场景：同时发送多个相同租户、相同幂等键和相同请求参数的创建请求，验证最终只有一条订单、只有一份报价快照且没有重复审计业务记录。

## 五、轨迹回调规则

### TRACK-001 回调事件按物流商、物流单号和事件 ID 幂等

- 规则：物流轨迹回调业务键统一为 `provider_id + tracking_no + event_id`，数据库使用 `UNIQUE(provider_id, tracking_no, event_id)`；重复事件返回幂等成功，但不能重复保存业务影响、重复推进订单状态或重复创建审计记录。
- 正常场景：首次收到一组物流商、物流单号和事件 ID，保存事件并处理订单状态。
- 边界场景：相同业务键重复到达且报文内容相同，返回幂等成功，不重复产生状态变更、费用影响或审计记录。
- 异常场景：相同业务键对应不同报文，记录幂等冲突异常并进入人工/重试处理；不能覆盖首次原始报文。

### TRACK-002 保存合法轨迹和原始信息

- 规则：所有合法轨迹都必须保存原始报文、`event_time`、`received_time` 和关联订单。
- 正常场景：合法运输节点被保存并可追溯原始报文。
- 边界场景：事件时间早于接收时间，仍保留两个时间并按事件时间展示。
- 异常场景：原始报文或事件时间缺失，事件不能作为完整合法轨迹落库。

### TRACK-003 展示按 event_time 排序

- 规则：轨迹展示顺序按 `event_time`，不按接收顺序；接收时间用于审计和排查延迟。
- 正常场景：先收到的晚事件和后收到的早事件展示为事件时间顺序。
- 边界场景：两个事件时间相同，使用稳定的事件 ID或接收时间作为次级排序依据。
- 异常场景：页面或接口按 `received_time` 作为业务轨迹顺序，属于展示错误。

### TRACK-004 订单状态只能向前推进

- 规则：合法轨迹可以推动订单状态前进，但不能使当前订单状态回退。
- 正常场景：订单从 `IN_TRANSIT` 收到签收事件后推进到 `DELIVERED`。
- 边界场景：迟到的较早事件仍保存，但不改变已推进的当前状态。
- 异常场景：迟到的出库事件试图将 `IN_TRANSIT` 回退为 `OUTBOUND`，系统拒绝状态变更并记录异常。

### TRACK-005 非法状态跳转记录异常并支持重试

- 规则：无法映射到状态机合法路径的回调必须记录异常，保留重试所需信息，不得静默丢弃。
- 正常场景：回调状态合法，正常处理完成。
- 边界场景：外部状态未知但原始报文完整，进入待重试异常队列。
- 异常场景：同一非法事件无限重复重试，系统应具备重试次数或人工介入边界。

## 六、账单导入与费用对账规则

### BILL-001 第一版使用统一 CSV 模板

- 规则：第一版账单导入只接受约定的统一 CSV 模板。
- 正常场景：物流商系统生成符合模板的 CSV 并成功导入。
- 边界场景：文件包含空行或允许为空的可选列，按模板规则处理。
- 异常场景：上传 Excel、未知列或编码不符合约定的文件，批次失败并返回原因。

### BILL-002 CSV 转换为统一账单明细 DTO

- 规则：系统读取 CSV 后必须转换为内部统一账单明细 DTO，再进入校验和对账流程。
- 正常场景：模板行转换为标准渠道、订单、金额和费用项字段。
- 边界场景：可选字段为空但不影响对账的行，转换成功并保留空值语义。
- 异常场景：金额、订单号或费用项无法转换，行级失败，不得生成不完整明细。

### BILL-003 保存导入批次和文件摘要

- 规则：必须保存导入批次、文件摘要、总行数、成功数量、失败数量和行级错误。
- 正常场景：批次完成后可查看文件摘要和成功/失败统计。
- 边界场景：部分成功、部分失败时批次保留两类结果，不把批次伪装成全成功。
- 异常场景：文件内容已改变但仍复用旧摘要，系统应拒绝或记录摘要不一致。

### BILL-004 金额完全一致时自动关闭对账

- 规则：系统核对后金额完全一致且必要业务关联完整时，自动关闭对账记录。
- 正常场景：报价/复称费用与账单金额一致，对账自动关闭。
- 边界场景：金额在统一精度下完全一致，但原始展示精度不同，按统一精度判断。
- 异常场景：金额一致但订单关联缺失或账单行非法，不得自动关闭。

### BILL-005 非零差异必须财务确认

- 规则：任何非零差异都必须由财务人员确认后才能关闭；第一版不实现小额差异自动关闭。
- 正常场景：财务人员选择处理方式、填写备注并确认差异，对账关闭。
- 边界场景：差异为最小货币单位，仍属于非零差异，不能自动关闭。
- 异常场景：商家操作员或系统自动任务尝试关闭非零差异，系统拒绝。

### BILL-006 财务处理必须可审计

- 规则：财务处理必须记录处理方式、备注、处理人、处理时间和审计日志。
- 正常场景：财务人员确认差异后，处理记录和审计日志完整保存。
- 边界场景：财务人员补充备注或更正处理方式，保留变更历史而非覆盖原记录。
- 异常场景：无处理方式、无备注或无操作人信息仍关闭对账，系统拒绝。
