# ShipFlow 企业级跨境物流与电商履约 ERP 差距审计

> 审计快照：2026-08-30，Asia/Shanghai。本文只陈述本次从源码、静态 OpenAPI、只读数据库查询、当前运行实例和真实测试获得的证据；页面存在不等于业务闭环完成。

## 1. 当前证据边界

- 当前分支为 `feature/logistics-business`，工作树存在大量既有未提交改动，主要涉及账单/对账、异常索赔、前端 ERP 组件和 OpenAPI；本次不清理、不重置、不覆盖这些改动。
- 只读数据库确认 `SELECT DATABASE()` 为 `shipflow`，MySQL `8.0.46`，系统时区 UTC。`flyway_schema_history` 观测到 V012 至 V023 均为成功；应用配置仍关闭 Flyway，且 V023 源文件尚未纳入 Git，因此不能由此推断当前应用曾受控执行迁移。
- 数据库存在真实业务事实：15 个订单、13 个包裹、12 条复称、9 条出库、12 个物流商订单、4 张面单、44 条 `shipment_tracking_event`、1 个异常、2 条异常处理记录、1 份证据、3 个账单批次、10 条账单明细、5 条对账、6 条对账处理历史、180 条幂等记录和 208 条审计记录。这里只记录聚合数量，不读取或披露客户明细。
- JDK 21.0.11 Maven 全量测试：97 个测试套件、420 个测试，失败 0、错误 0、跳过 0。前端 typecheck 与生产构建通过；最终 Vitest 30 个文件、122 个测试通过。
- 静态 OpenAPI 有 114 个 operationId 声明但只有 113 个唯一值，`listTrackingEvents` 重复；当前运行实例有 114 个运行时 operationId 且命名大范围依赖方法名，静态与运行时 operationId 契约明显漂移。

## 3. 差距优先级

### P0

1. 首页指标口径与下钻不一致：部分 SQL 没有应用响应中声明的时间窗，目标查询也没有携带同一时间范围，仓库/轨迹部分筛选在前端被明确标记为“接口尚不支持”。
2. 静态 OpenAPI operationId 重复，且运行时 operationId 与静态契约大范围漂移，客户端生成与回归基线不可靠。
3. 物流回调虽能验签、去重、保留乱序事件和审计，但没有重试调度、死信和人工重放路径。
4. 账单金额匹配粒度不足：缺少费用类型级匹配、币种/汇率快照、税费与附加费规则；当前总额比较不能支撑企业级结算准确性。
5. 幂等覆盖不完整：需要逐一梳理所有业务写接口，区分认证类请求与必须强制幂等的业务写入，并补齐处理中超时、过期记录恢复和人工重放。
6. 外部服务配置存在源码默认凭据，必须移除默认值、轮换现有凭据并增加启动校验和密钥扫描。
7. Flyway 运行治理断裂：应用关闭 Flyway、数据库已到 V023、V023 源文件未跟踪；需要发布审计证明和 checksum 对齐，不能再次盲目执行。

### P1

1. 订单导入、审核、规则分仓、仓库拣配/打包/交接、物流下单/面单/轨迹、异常、账单和结算尚未形成统一可追溯状态链。
2. 多物流商接入仍以顺丰能力为主，缺少标准适配器、调用日志、超时/退避重试、熔断、死信与人工补偿。
3. 仓库缺少库位、波次、拣货、包装、库存变更与盘点作业。
4. 异常缺少 SLA 升级、自动指派、承运商责任协同和赔付入账。
5. 账单需要 RFC 4180 解析、逐费用项匹配、重复来源识别、错误行修复/重跑、差异原因字典、审批权限分离和结算/冲销。
6. 订单、物流、异常、账单、对账和审计虽有部分关联查询，但前端尚无完整双向跳转和统一时间线。

### P2

1. 无 Shopify/Amazon/Shopee/Lazada 等平台连接器、订单增量同步、Webhook、水位与补偿任务。
2. 无 SKU 主数据、库存台账、预占/释放、仓间调拨与平台库存回传。
3. 无 ETA 模型、SLA 配置、承运商准时率/异常率/成本绩效、仓库人效和费用趋势事实层。
4. 无企业报表中心、可审计导出任务、大数据量异步导出、预测与预警。
5. 角色化工作台尚未形成商户、仓库、财务、客服各自独立的指标字典、待办优先级与批量操作权限模型。

## 4. 本轮首个改进模块

先修复“运营首页指标与下钻一致性”：以同一后端谓词产生指标 `count` 和下钻 `total`，为每个指标提供定义、事实来源、时间字段、时区、闭开区间与目标查询；前端只展示后端结果，不再为指标自行推算。该模块不执行数据库迁移。

## 5. 仍需负责人确认的问题

1. 首页“待处理订单”按任务条数、去重订单数还是包裹数统计？同一订单进入财务与异常待办时是否允许重复计入跨域总待办？
2. 财务系统金额应以订单当前费用、已确认费用还是不可变计费快照为对账基准？多费用项与税费的精度、舍入和汇率来源是什么？
3. 乱序轨迹允许自动推进的时间窗口和人工重放审批角色是什么？是否要求原始回调不可变归档及保留期限？
4. Flyway 由应用、CI/CD 还是 DBA 执行？V023 当前数据库记录的发布单、执行人和 checksum 由谁确认？
5. P2 首批电商平台与承运商优先级、接口配额、Webhook 安全规范和数据留存要求是什么？

## 6. 本次真实登录浏览器证据

- 使用现有 Chrome 登录态只读验收，身份为租户 1 的租户管理员；未读取 Cookie、Authorization、密码或客户请求体，未触发任何业务写操作。
- 订单页真实渲染授权范围内的分页列表、状态、目的地、渠道、筛选、排序和导出控件。
- 仓库页对该登录角色真实返回“无权访问”，说明浏览器权限边界生效；该项是 403 边界通过，不是仓库业务验收通过。
- 轨迹页对既有授权订单执行只读查询并渲染 8 个时间线事件。
- 异常与索赔页渲染 1 条真实列表记录；账单页渲染 3 个批次，切换费用对账后渲染 5 条真实对账记录，与只读数据库聚合数量一致。
- 刷新首页后，新前端已不再复制财务 breakdown 为额外首页指标；但运行中的 8080 后端仍是修改前实例，响应不包含本轮新增的 definition/dataSource/timeField/unit 及下钻时间参数。因此本轮后端运行态验收为 BLOCKED，不能用编译测试或旧进程页面替代。
