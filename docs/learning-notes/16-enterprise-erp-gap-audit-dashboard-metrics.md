# 企业 ERP 差距审计与首页指标口径学习笔记

日期：2026-08-30（Asia/Shanghai）

## 本模块完成的内容

- 基于当前源码、静态/运行时 OpenAPI、只读 MySQL 与当前测试建立企业 ERP 差距审计，未把页面存在报告为业务闭环完成。
- `operations/workbench` 的指标和待办统一使用调用方租户、用户、ACTIVE 店铺范围以及同一 UTC 闭开时间窗 `[from, to)`。
- 为每个首页核心指标返回业务定义、事实来源、实际时间字段和 `ORDER_COUNT`/`TASK_COUNT` 单位；前端显示这些口径，不再把财务 breakdown 复制成额外首页指标。
- 指标目标 URL 保留 `timeRange/from/to`，避免跳转时静默丢失首页统计窗口。
- 静态 OpenAPI 补充指标口径字段，并消除重复的 `listTrackingEvents` operationId；运行时 operationId 与静态契约的大范围漂移仍需独立治理。

## 关键业务认识

- “待处理订单”与“待处理任务”不是同一单位。财务聚合允许同一订单产生费用确认、账单错误、对账差异和索赔财务复核等多条任务，必须明确计数单位，不能用前端加总冒充去重订单数。
- 响应里声明时间范围但 SQL 未应用该范围，比没有时间范围更危险，因为它会制造看似精确但不可复核的指标。
- 指标口径完整至少需要：参与方范围、事实来源、状态谓词、时间字段、时区、区间边界、去重键、单位和下钻查询。
- 本轮只统一了首页快照的时间语义与口径元数据。仓库、轨迹、财务的现有列表仍不能表达全部首页谓词，因此“指标 count = 下钻 total”尚未闭环，必须继续增加后端同谓词下钻接口或扩展现有列表契约。

- 修改前基线：JDK 21.0.11 Maven 97 个套件、420 个测试通过；前端 typecheck 通过；30 个 Vitest 文件、121 个测试通过。
- 修改后：后端仍为 97 个套件、420 个测试通过；前端 typecheck、生产构建以及 30 个 Vitest 文件、122 个测试通过。
- 修改后定向：Operations Service、Mapper XML、WebMvc 测试通过；前端 typecheck 通过；工作台目标、工作台工具与首页布局 3 个文件、16 个测试通过。
- 数据库仅执行只读查询；未执行 Flyway、DDL、DML、外部物流调用、Git 提交或推送。
- 真实登录 Chrome 只读验证：订单列表渲染；仓库按当前角色返回无权访问；既有订单轨迹渲染 8 个事件；异常列表 1 条；账单批次 3 条；费用对账 5 条。运行中的后端未重启，因此新增指标口径字段和 SQL 只能报告为源码/测试 PASS、运行态 BLOCKED。

## 后续必须继续的 P0

2. 修复账单错误指标对 `shipment_order_id IS NULL` 错误行的可见性与计数语义，同时保持店铺范围和财务角色权限。
3. 为轨迹 `RETRY/REJECTED` 事实增加退避重试、死信和经审计的人工重放。

5. 对齐静态 OpenAPI 与运行时 operationId，加入自动契约差异测试。
