# ShipFlow 订单状态机

## 1. 状态集合

### 主流程状态

`DRAFT` → `PENDING_INBOUND` → `INBOUND` → `READY_FOR_OUTBOUND` → `OUTBOUND` → `IN_TRANSIT` → `DELIVERED`

### 条件分支

复称后费用增加时：

`INBOUND` → `PENDING_PRICE_CONFIRMATION` → `READY_FOR_OUTBOUND`

### 终止或特殊状态

- `CANCELLED`：订单取消后不可继续正常履约。
- `RETURNED`：订单进入退回流程并完成退回处理。
- `LOST`：订单确认丢失。

地址异常、清关异常和运输异常不直接替代主订单状态，必须创建独立异常单；异常单的处理结果可以触发订单进入 `RETURNED` 或 `LOST` 等特殊状态。

## 2. 状态转移表

| 当前状态 | 允许进入的下一状态 | 触发角色 | 前置条件 | 非法操作 |
| --- | --- | --- | --- | --- |
| `DRAFT` | `PENDING_INBOUND`、`CANCELLED` | 商家操作员、商家管理员；平台授权人员可人工纠正 | 订单已引用有效 `quote_id`、报价快照已保存；取消需订单尚未进入仓库流程 | 直接进入 `INBOUND`、`OUTBOUND`、`IN_TRANSIT` 或 `DELIVERED`；无有效报价创建订单；无原因人工纠正 |
| `PENDING_INBOUND` | `INBOUND`、`CANCELLED` | 仓库人员负责入库；商家管理员、商家操作员可取消；平台授权人员可人工纠正 | 订单已提交入库；入库确认需匹配租户、订单和包裹 | 未入库直接出库、运输或签收；重复入库；入库后再直接取消 |
| `INBOUND` | `READY_FOR_OUTBOUND`、`PENDING_PRICE_CONFIRMATION`、`RETURNED` | 仓库人员负责复称并触发费用重算；商家用户负责价格确认；退回原则上由物流商回调，平台授权人员可人工纠正 | 已保存仓库实际重量和尺寸；费用不变或降低时可进入可出库；费用增加必须进入价格确认；停止发货必须进入退回流程 | 未完成复称直接出库；费用增加跳过价格确认；商家用户直接标记取消、签收、丢失或退回；普通轨迹回退状态 |
| `PENDING_PRICE_CONFIRMATION` | `READY_FOR_OUTBOUND`、`RETURNED` | 商家管理员或商家操作员确认新费用；退回原则上由物流商回调；平台授权人员可人工纠正 | 已生成新费用和调整记录；商家明确确认新价格 | 未确认价格直接出库；非商家角色确认；重复确认产生重复调整；财务人员修改物流状态 |
| `READY_FOR_OUTBOUND` | `OUTBOUND`、`RETURNED` | 仓库人员负责出库；退回原则上由物流商回调；平台授权人员可人工纠正 | 费用确认完成或费用无需确认；出库资料完整，仓库作业完成 | 仍有待确认价格时出库；商家用户直接标记运输、签收或丢失；财务人员修改物流状态 |
| `OUTBOUND` | `IN_TRANSIT`、`RETURNED`、`LOST` | 物流商系统回调；平台授权人员可人工纠正；仓库人员只负责完成出库事实 | 已完成出库和物流商交接；运输事件合法且订单匹配 | 商家用户或财务人员直接标记运输、签收、退回或丢失；未交接直接签收；迟到事件回退 |
| `IN_TRANSIT` | `DELIVERED`、`RETURNED`、`LOST` | 原则上由物流商系统回调；平台授权人员可人工纠正 | 收到合法签收、退回或丢失事件；事件通过幂等和状态机校验 | 商家用户直接标记签收、丢失或退回；财务人员修改物流状态；回退到 `OUTBOUND` |
| `DELIVERED` | 无主流程下一状态；可创建异常单 | 物流商系统回调完成；平台授权人员可人工纠正；商家用户只能创建异常或索赔 | 交付事件合法；后续问题通过异常单与索赔处理 | 商家用户直接标记或回退物流状态；财务人员修改物流状态；修改历史报价快照 |
| `CANCELLED` | 无 | 商家管理员、商家操作员；平台授权人员可人工纠正 | 仅允许在 `DRAFT` 或 `PENDING_INBOUND` 阶段取消 | 入库完成后直接取消；取消后重新入库、出库或运输 |
| `RETURNED` | 无；可通过异常单记录后续索赔 | 原则上物流商系统回调；平台授权人员可人工纠正 | 退回事件合法或平台授权人员完成带原因的人工纠正 | 商家用户直接标记退回；财务人员修改状态；退回后恢复普通履约主流程 |
| `LOST` | 无；可通过异常单记录后续索赔 | 原则上物流商系统回调；平台授权人员可人工纠正 | 丢失事件合法或平台授权人员完成带原因的人工纠正 | 商家用户直接标记丢失；财务人员修改状态；丢失后恢复运输或签收 |

## 3. 状态转移业务说明

### 3.1 创建与入库

订单创建后处于 `DRAFT`。只有订单引用有效报价、保存报价快照并提交仓库作业后，才能进入 `PENDING_INBOUND`。仓库人员确认包裹入库后进入 `INBOUND`。`DRAFT` 和 `PENDING_INBOUND` 允许取消；完成入库后停止发货必须进入退回流程，不直接进入 `CANCELLED`。

### 3.2 复称与价格确认

入库后由仓库人员保存仓库实际重量和尺寸，并重新计算仓库实际体积重量、复称后的计费重量与费用：

- 费用不变：自动进入 `READY_FOR_OUTBOUND`。
- 费用降低：自动更新费用、记录调整并进入 `READY_FOR_OUTBOUND`。
- 费用增加：进入 `PENDING_PRICE_CONFIRMATION`；商家确认新价格后进入 `READY_FOR_OUTBOUND`。

### 3.3 出库与运输

只有 `READY_FOR_OUTBOUND` 订单才允许仓库出库并进入 `OUTBOUND`。完成物流商交接、收到合法运输事件后进入 `IN_TRANSIT`，收到合法签收事件后进入 `DELIVERED`。

### 3.4 轨迹事件与状态推进

轨迹事件按 `provider_id + tracking_no + event_id` 幂等去重并全部保存。重复事件返回幂等成功，但不能重复保存业务影响、重复推进状态或重复创建审计记录。展示按 `event_time` 排序，当前订单状态只能向前推进；迟到事件可以补充轨迹历史，但不得使订单状态回退。非法跳转记录异常并进入重试或人工处理流程。

`IN_TRANSIT`、`DELIVERED`、`RETURNED`、`LOST` 原则上由物流商回调触发。商家用户不得直接把订单标记为 `DELIVERED`、`LOST` 或 `RETURNED`；人工纠正物流结果只能由平台授权人员执行，并记录纠正原因和审计日志。财务人员不得修改订单物流履约状态。

## 4. 通用非法操作处理

所有非法状态操作必须：

1. 不修改订单当前状态和报价快照。
2. 返回明确的业务错误。
3. 记录操作者、租户、请求关联信息和失败原因。
4. 对外部轨迹非法跳转保留原始报文，并支持受控重试。

重复请求必须遵循幂等规则，不得重复创建状态变更、费用调整、出库记录或审计结果。
